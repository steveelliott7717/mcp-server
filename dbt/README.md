# mcp_analytics — a dbt project over the MCP server's Postgres schemas

A dbt project modelling the `health`, `finance` and `professional_profile`
schemas from this repository's MCP server, running on **DuckDB with committed
seed data** so it builds reproducibly without credentials or a network
connection.

```bash
pip install dbt-duckdb
cd dbt
dbt build --profiles-dir .
```

That is the whole setup. No database to provision, no secrets, no `.env`.

---

## What is real and what is synthetic

This distinction matters, so it is stated first rather than buried.

| | Source |
|---|---|
| **Schema shape** — table names, column names, types, constraints, foreign keys | **Real.** Taken from [`../supabase/schema/`](../supabase/schema/), the DDL checked into this repository. |
| **Transformation logic** — BMR formula, step-calorie lag, macro policy, rolling averages | **Real.** Ported from `health.rpc_snapshot_daily_overview()` and the trigger functions in [`../supabase/schema/health.sql`](../supabase/schema/health.sql). |
| **Rows** | **Synthetic.** Generated by [`seeds/generate_seeds.py`](seeds/generate_seeds.py) with a seeded RNG. |

Nothing here has ever been pointed at a production database. The seed generator
writes CSVs and does nothing else; the DuckDB profile reads a local file. There
is no code path from this project to live data.

The generator is committed rather than just its output, so the provenance of
every row is inspectable and the dataset is reproducible:

```bash
python seeds/generate_seeds.py --seed 20260906   # regenerates all 13 CSVs
```

## Why this project exists

`health.rpc_snapshot_daily_overview()` is a ~90-line plpgsql procedure invoked
by cron. It calculates daily calorie and macro targets through a chain of eight
CTEs: Mifflin-St Jeor BMR against a 3-day rolling bodyweight, activity calories
from three sources with a deliberate two-day lag on wearable data, a goal
adjustment from the active training program, and a macro split backsolved from
the total.

The logic was already correct in intent. What it lacked was **testability,
lineage, and a grain wider than "today"**. This project ports it to a dbt DAG:

- **17 models** across staging → intermediate → marts
- **74 generic tests + 4 singular tests**, every one derived from a constraint
  or a documented behaviour in the real DDL
- **13 seeds**, 577 rows

```
seeds ──► staging (13) ──► intermediate (4) ──► marts (3)
                            int_date_spine
                            int_weight_trends      fct_daily_overview
                            int_activity_kcal      fct_meal_consumption_daily
                            int_calorie_targets    fct_spend_monthly
```

### Three concrete differences from the procedure

**1. Grain.** The procedure upserts one row for `CURRENT_DATE` per cron run and
cannot be backfilled — a corrected formula reaches tomorrow and never touches
history. Every model here builds on a date spine, so all 62 days recompute on
every run.

**2. Recompute vs. accumulate.** In production, `calories_logged` and its
siblings are maintained incrementally by the `f_update_daily_overview_consumption`
trigger, which adds to a running total on each `meal_logs` insert. That is fast
and cannot self-heal: an edited or deleted meal leaves the total permanently
wrong, because nothing re-derives it. `fct_meal_consumption_daily` aggregates
instead, so the figures are correct by construction on each run. Both sides of
that trade are legitimate; the point is that dbt makes the choice explicit.

**3. Named constants.** The pound-to-kilogram factor appears three times in
`health.sql` with **two different values** — `0.4536` in the snapshot RPC,
`0.453592` in `auto_calc_step_calories()` and `health_calc_strength_metrics()`.
Inline in three procedure bodies, that inconsistency is invisible. Extracted to
[`macros/lbs_to_kg.sql`](macros/lbs_to_kg.sql), it had to be resolved.

## What the port surfaced

**The macro policy and the carbohydrate backsolve disagree in the production
procedure.**

`rpc_snapshot_daily_overview()` documents and computes its macro targets as
protein 1 g/lb and **fat 0.4 g/lb**. But the carbohydrate remainder subtracts
fat calories using **0.3**:

```sql
ROUND((
  bmr + activity + goal
  - (weight_lbs * 4 + weight_lbs * 0.3 * 9)   -- 0.3, not the 0.4 prescribed above
) / 4, 0) AS carbs_g
```

So the fat grams prescribed and the fat calories deducted differ, and
carbohydrates absorb the gap. The macro split therefore does not sum back to
the calorie target it was derived from.

[`tests/assert_macro_kcal_reconciles.sql`](tests/assert_macro_kcal_reconciles.sql)
asserts `protein·4 + fat·9 + carbs·4 ≈ total_kcal_target`. The models use the
consistent constant, so it passes. Reproducing the source behaviour makes it
fail on every row:

```bash
dbt build --profiles-dir . --select int_calorie_targets+ \
          --vars '{fat_g_per_lb_deduction: 0.3}'
# FAIL 62 assert_macro_kcal_reconciles
```

Measured drift on this dataset: **156.4–170.0 kcal/day, mean 163.9**. The
algebra predicts `0.9 kcal × bodyweight`, which at the dataset's mean 182 lb is
163.8 — matching the measurement to 0.1 kcal, which confirms the mechanism
rather than just the symptom.

The production database asserts no relationship between the macro columns and
the calorie column, which is why this survived in a shipped procedure. One test
was enough to find it.

*Scope note:* this is a finding about internal consistency of the arithmetic,
demonstrated against synthetic rows. Whether the intended policy is 0.3 or 0.4
is a question for whoever set the policy — what the test establishes is that
the procedure cannot be doing both, which it currently claims to.

## Reconstructed objects

`health.sql` defines 8 tables but **references 6 objects it never defines**.
Four are load-bearing for the snapshot RPC, so a faithful port needs them.
Their columns were inferred from usage and are marked as reconstructions in
both the model SQL and the schema documentation:

| Object | Referenced by | Reconstructed from |
|---|---|---|
| `health.v_weight_trends` | 5 call sites | Documented as "3-day and 7-day rolling averages" over `weight_logs`; columns `log_date`, `avg_3day`, `avg_7day` are read by name in the RPC. → [`int_weight_trends`](models/intermediate/int_weight_trends.sql) |
| `health.bike_logs` | snapshot RPC | `scheduled_date`, `calories_burned` read by name. → [`stg_bike_logs`](models/staging/stg_bike_logs.sql) |
| `health.weekly_programs` | snapshot RPC | `start_date`, `kcal_adjustment` read by name. → [`stg_weekly_programs`](models/staging/stg_weekly_programs.sql) |
| `health.exercises` | strength trigger | Not modelled. The RPE/movement-class calorie model depends on six columns of metadata with no DDL; `calories_burned` is taken as a source column instead. |
| `health.batch_prep` | `meal_logs.batch_prep_id` | Not modelled — third meal source, unused by the marts. |
| `health.household_items` | `finance.purchases` FK | Not modelled — no downstream consumer. |

Where an object could not be responsibly reconstructed it was left out and said
so, rather than invented.

`int_weight_trends` also makes two deliberate improvements over a naive port:
rolling windows are `RANGE` over calendar days rather than `ROWS` over
observations, so a missed weigh-in cannot silently stretch a 3-day average
across a week; and the carried-forward `avg_3day_filled` centralises a fallback
that the three production call sites each hardcode independently as `70.0` kg.

## Layout

```
dbt/
├── dbt_project.yml
├── profiles.yml                  duckdb, local file, no credentials
├── seeds/
│   ├── generate_seeds.py         deterministic synthetic data generator
│   └── *.csv                     13 seeds, 577 rows
├── models/
│   ├── staging/                  13 models — typing, renaming, 1:1 with source
│   ├── intermediate/             4 models — the RPC's CTE chain, decomposed
│   └── marts/                    3 models — fct_daily_overview and friends
├── macros/                       mifflin_st_jeor, lbs_to_kg
└── tests/                        4 singular tests
```

Tests are derived from the real DDL rather than invented: `unique` on
`snapshot_date` mirrors `daily_overview_snapshot_snapshot_date_key`;
`accepted_values` on `frequency` mirrors the CHECK constraint enumerating
`daily|weekly|biweekly|monthly|quarterly|yearly`; `relationships` on
`recipe_ingredients` and `recurring_purchase_charges` mirror declared foreign
keys. The singular tests cover what the schema cannot express — macro
reconciliation, trigger-column drift, and a plausibility range on `weight_lbs`,
which is `NOT NULL` but otherwise unconstrained in a column three separate
calculations depend on.

## Relationship to the rest of this repository

Standalone and inert. It reads `../supabase/schema/*.sql` as reference material
only — never executed — and the MCP server does not load, scan or import this
directory. Build artifacts (`target/`, `logs/`, `*.duckdb`) are gitignored.
